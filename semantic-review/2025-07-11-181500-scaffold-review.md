# VedicMojoAI Project Scaffold

An 18-agent Vedic astrology pipeline implemented as a Next.js 14 TypeScript monorepo with Prisma/PostgreSQL persistence, Server-Sent Events for live progress, and a deterministic Vimshottari dasha engine. The scaffold establishes the full architecture from chart submission through Wave 1–4 agent execution to HTML report rendering. The code closely follows the HLD's prescribed layering, context-injection strategy, and halt-gate semantics.

Watch for: the `computeVimshottari` integrity check will throw for every chart where the Moon is not at 0° of a nakshatra boundary — the sum formula is wrong (confirmed); the verification agent has no AGENT_CATALOGUE entry so all follow-up queries crash (confirmed); the `POST /api/runs/{id}/rerun` route from the HLD is missing (confirmed); the Dockerfile copies a non-existent `public/` directory (confirmed); and orchestrator feeds empty context to 4A/4C when 4X returns empty content (confirmed).

## High-level view

The Vimshottari computation uses correct period-duration formulas (each sub-level divides by 120) and sources YEAR_DAYS = 365.2425 from constants.ts. However, the self-verification check sums all 9 mahadashas — the partial first one plus 8 full ones — then compares against 120 × YEAR_DAYS. The sum will always be less than 120 years by the consumed portion of the birth dasha, so the integrity check will throw `DashaIntegrityError` for every chart where the Moon has any traversal within its nakshatra.

The orchestrator implements the halt gate correctly: after 4A, critical errors block 4B/4C, persist halt_reason, emit SSE critical_error, and throw PipelineHaltError. Context assembly for 4C restricts input to chart_summary + fact_summary + 4A + 4B per the HLD. The gap: when 4X returns empty content, `context.factSummary` stays null, and downstream agents proceed without their primary input — no error, just silently degraded output.

The API layer covers all HLD routes except `POST /api/runs/{id}/rerun?from_wave={n}`. The planner is deterministic as specified, but `wave2.ts` exports a domain-scoped filter for Wave 3 context injection that the orchestrator never calls — all Wave 2 outputs reach all Wave 3 agents, inflating token usage.

The AGENT_CATALOGUE omits the `'verification'` agent entirely. Since `executeAgent` throws on unknown agent IDs, every follow-up query (which the planner routes through verification) will crash at runtime.

The Dockerfile copies `public/` (doesn't exist) and runs `prisma migrate deploy` (no migrations directory exists). Neither Docker builds nor local dev will work without generating a Prisma migration first.

## Vimshottari dasha computation — the arithmetic bug

The bug is in the self-verification:

```typescript
const totalDays = mahadashas.reduce((sum, md) => sum + md.duration_days, 0)
const expectedDays = TOTAL_DASHA_YEARS * YEAR_DAYS  // 120 × 365.2425
```

The 9 mahadashas are: [balanceYears as partial first MD, then 8 full MDs cycling through the sequence]. The actual sum in years is `balanceYears + (120 - birthLordYears)`, which equals 120 only when `balanceYears == birthLordYears` (Moon at nakshatra boundary). For a typical chart with Moon at 50% traversal through a Venus nakshatra, the sum would be `10 + (120 - 20) = 110 years` — the check throws immediately.

Simplest correct check — compute expected from the same allocations:

```typescript
const expectedDays = mahadashas.reduce((sum, md) => sum + md.duration_days, 0)
// This is tautological. Better: verify contiguity and AD sub-sums.
```

The right assertion is: (a) each MD's antardashas sum to the MD's duration (± tolerance), and (b) MD[n].end === MD[n+1].start for all consecutive pairs. These catch floating-point drift without encoding an incorrect total.

## Verification agent — missing runtime metadata

`AGENT_CATALOGUE` lists 19 entries (1A–1D, 2A–2G, 3A–3D, 4X, 4A–4C) but not `'verification'`. The planner adds `'verification'` to every follow-up plan (line: `agentSet.add('verification')`). When the orchestrator reaches it:

```typescript
const agentMeta = AGENT_CATALOGUE.find((a) => a.id === agentId)
if (!agentMeta) {
  throw new Error(`Unknown agent: ${agentId}`)
}
```

This crashes the run, marks it failed, and the user sees no report. The fix requires adding the catalogue entry and creating a `verification.md` prompt file in `prompts/agents/`.

## Orchestrator context assembly — Wave 3 token inflation

The `assemblePrompt` function for agents starting with `'3'` injects the full `context.wave2Deltas` map:

```typescript
} else if (agentId.startsWith('3')) {
  if (Object.keys(context.wave2Deltas).length > 0) {
    parts.push('--- WAVE 2 DOMAIN OUTPUTS ---')
    parts.push(JSON.stringify(context.wave2Deltas, null, 1))
  }
}
```

Meanwhile, `engine/waves/wave2.ts` exports `getRelevantWave2ForWave3(wave3Agent)` that maps each Wave 3 agent to its relevant Wave 2 inputs. For a "full" run, agent 3B (Financial Freedom) receives outputs from 2A, 2B, 2C, 2D, 2E, 2F, 2G when it only needs 2C. At an estimated ~2K tokens per agent output, this adds ~12K unnecessary tokens per Wave 3 agent call.

## Null factSummary propagation

The flow for factSummary:

1. `executeAgent('4X', ...)` calls LLM, gets `response.content`
2. WaveOutput is saved with `factSummary: response.content` (raw text)
3. Orchestrator reads it back: `const output = await getLatestOutput(runId, '4X')`
4. Sets `context.factSummary = output?.factSummary ?? null`

If the LLM returns an empty string (rate limit fallback, malformed response that `callLLM` doesn't throw on), factSummary becomes `""`. The assemblePrompt for 4A and 4C inserts `--- FACT SUMMARY ---\n\n` with no content. These agents are designed to analyze the fact summary — receiving nothing means they operate on chart_summary alone, potentially missing all Wave 2/3 findings. A truthy check after step 4 would catch this.

## Docker and local dev blockers

The Dockerfile's `COPY --from=builder /app/public ./public` line will fail because Next.js only creates `/app/public` if the directory exists in source. No static assets have been added to the scaffold.

No migrations exist. The docker-entrypoint runs `npx prisma migrate deploy` which requires `prisma/migrations/` with at least one migration. The fix is `npx prisma migrate dev --name init` during scaffolding to generate the initial migration from the schema.

The `next.config.ts` lists only `@prisma/client` in `serverComponentsExternalPackages`. The AI SDK packages (`ai`, `@ai-sdk/anthropic`, `@ai-sdk/openai`) might need to be listed here for the standalone build to bundle them correctly — they use dynamic imports and native fetch that can trip up webpack's bundler in standalone mode.

## Custom agent selection bypass

The `POST /api/runs` handler passes `customAgents` directly to `resolvePlan()` without calling `validateAgentSelection()`. A request with `customAgents: ['4C']` (missing 4X dependency) will produce a plan that crashes at runtime when 4C tries to read a factSummary that was never produced. The validation function exists and catches this — it just needs to be called before `resolvePlan`.
