# Deterministic Vedic chart computation engine (Swiss Ephemeris + varga + ashtakavarga)

This change adds a self-contained chart engine under `engine/compute/` that turns date/time/lat/long into sidereal planetary positions (Lahiri ayanamsa via `swisseph-v2`), six divisional charts (D1/D4/D7/D9/D10/D30), nakshatra/pada, Chara Karakas, and Ashtakavarga, then wires it to a stateless `POST /api/compute` endpoint that also builds the Vimshottari dasha tree. The stated goal is to replace LLM-guessed chart data with deterministic, classically-correct math. The astronomy layer (Julian Day conversion, sidereal longitudes, ascendant, Ketu-from-Rahu) is sound, but several of the astrological derivation rules are miscoded and produce classically-wrong output.

Watch for: the D9 Navamsa formula (**confirmed** wrong for 8 of every 12 signs — the core varga for marriage/strength), the D4 rule for even signs (**confirmed** wrong), two data-entry errors in the Ashtakavarga bindu tables (**confirmed** — Sun BAV and Venus BAV totals off), the D30 odd-sign Venus mapping (**likely** wrong), and a server-local-timezone `Date` construction in the API route that makes dasha dates non-deterministic across deployments (**confirmed**). Separately, the engine silently runs on the Moshier fallback, not the Swiss Ephemeris files it names (**confirmed**, low impact).

## High-level view

The astronomy is the trustworthy part. `birthInputToJulianDay` converts local civil time to UT and hands it to `swe_julday`; the timezone subtraction and the day/month/year rollover arithmetic are correct across the ranges the validator allows. Sidereal mode is set to Lahiri before every ephemeris call, retrograde is read from longitude speed, and Ketu is derived as Rahu + 180°. No correctness issues here.

The divisional-chart layer is where the classical rules break down. D7 and D10 are correct. D1 is trivial and correct. But D9 Navamsa adds a spurious `signOffset * 9` term that corrupts the result for every sign whose position within its triplicity is not the first — i.e. two-thirds of the zodiac. D4 invents an odd/even distinction that isn't in the Parashari Chaturthamsa rule and shifts every even-sign result. D30 has correct segment boundaries but assigns the odd-sign Venus portion to Taurus (an even rashi) while every other planet in the odd column maps to its odd rashi, which is internally inconsistent and almost certainly a transcription slip.

The Ashtakavarga engine's mapping logic (count benefic houses from each contributor, mark the target sign) is correct, but the static bindu tables contain two extra entries: Sun-from-Moon and Venus-from-Mars. This pushes the Sun BAV total to 50 (should be 48), the Venus BAV to 53 (should be 52), and the SAV to 340 (should be the canonical 337).

Nakshatra/pada and Chara Karaka math are correct. The Chara Karaka header comment contradicts the code's default (comment says 8-karaka/include Rahu, code defaults to 7-karaka), which is a doc nit, not a math bug.

The API route computes the chart's Julian Day correctly in UT but then rebuilds the birth instant a second time as `new Date(year, month-1, day, ...)`, which is interpreted in the *server's* local timezone. That birth instant drives the whole dasha tree and is serialized with `toISOString()`, so the same birth data yields different dasha dates depending on where the server runs — directly at odds with the determinism goal.

Finally, the engine passes `SEFLG_SWIEPH` but no ephemeris path is ever set and no `.se1` files are bundled, so `swisseph-v2` silently falls back to the built-in Moshier model. Output is still ~arcsecond-accurate, so this is a labeling/accuracy-expectation issue rather than a failure.

### D9 Navamsa: spurious triplicity offset corrupts 8 of 12 signs

`computeD9Sign` picks the correct element-based starting sign — fire→Aries(1), earth→Capricorn(10), air→Libra(7), water→Cancer(4), keyed by `(signNumber-1) % 4`, which is correct because the zodiac cycles fire/earth/air/water in order. The classical navamsa from there is just `startSign + part` (part = 0–8), and that formula is naturally continuous: Aries's 9 navamsas end at Sagittarius, Taurus's begin at Capricorn, and so on around 108 navamsas.

The code instead computes `totalOffset = signOffset * 9 + part`, where `signOffset = (signNumber - 1) % 3`. That extra `signOffset * 9` term is not part of the element method and throws the result off by 9 navamsas (= 3 signs, since 9 mod 12 wraps) for any sign that isn't first in its triplicity.

```
long  30 (0° Taurus): code = Libra,      classical = Capricorn
long  40 (10° Taurus): code = Capricorn, classical = Aries
long 150 (0° Virgo):   code = Cancer,    classical = Capricorn
long 335 (5° Pisces):  code = Aquarius,  classical = Leo
```

Only signs with `signOffset == 0` (Aries, Cancer, Libra, Capricorn) come out right. The fix is to delete the `signOffset` term and use `((startSign - 1 + part) % 12) + 1`. This is the highest-impact bug in the change: D9 is the second-most-used chart in Vedic astrology and every navamsa-based interpretation downstream (marriage, dharma, planetary strength) inherits the error.

### D4 Chaturthamsa: an odd/even rule that shouldn't exist

The Parashari Chaturthamsa assigns the four 7°30' quarters of any sign to that sign and the 4th, 7th, and 10th from it — the four kendras — for all twelve signs, with no odd/even reversal. The odd branch in `computeD4Sign` implements exactly that (`startSign = signNumber`, advance by 3). The even branch starts three signs ahead (`(signNumber-1+3)`), which rotates the whole quarter sequence:

```
long 32 (2° Taurus):  code = Leo,     classical = Taurus
long 40 (10° Taurus): code = Scorpio, classical = Leo
```

Odd signs happen to come out correct. The fix is to drop the branch entirely and use `((signNumber - 1 + part*3) % 12) + 1` for all signs.

### D30 Trimshamsa: odd-sign Venus lands in the wrong rashi

The segment boundaries are right — odd signs split 5/5/8/7/5 into Mars/Saturn/Jupiter/Mercury/Venus, even signs mirror to 5/7/8/5/5 as Venus/Mercury/Jupiter/Saturn/Mars. The sign each lord maps to is where it drifts: for odd signs the code returns Aries(Mars), Aquarius(Saturn), Sagittarius(Jupiter), Gemini(Mercury) — all odd rashis — but the final Venus portion returns Taurus(2), an even rashi. Every other odd-column entry uses the planet's odd-numbered rashi; Venus's odd rashi is Libra(7). The even column is internally consistent (Taurus/Virgo/Pisces/Capricorn/Scorpio, all even). This reads as a copy error where the odd-sign Venus should be Libra. Worth confirming against the specific Trimshamsa convention the project intends, since D30 sign-assignment has some tradition variance, but the internal inconsistency is the tell.

### Ashtakavarga: two extra bindus inflate Sun, Venus, and SAV

The reduction logic is correct — for each reference planet, walk the 7 planets plus Lagna, and for each benefic house number counted from the contributor's sign, add a bindu to the target sign (`(contributorSign - 1 + houseNum - 1) % 12`). The bug is in the static `BINDU_TABLE` data. Two rows carry an extra entry versus the canonical BPHS tables:

```
Sun.Moon   = [3,6,7,8,10,11]  should be [3,6,10,11]   (extra 7,8)
Venus.Mars = [3,4,6,8,9,11,12] should be [3,4,6,9,11,12] (extra 8)
```

Verified totals against the canonical per-planet bindu counts:

```
Sun    50  (should be 48)   *** off by 2
Moon   49  OK
Mars   39  OK
Mercury 54 OK
Jupiter 56 OK
Venus  53  (should be 52)   *** off by 1
Saturn 39  OK
SAV   340  (should be 337)  *** off by 3
```

Because SAV is the sum of all seven BAVs, every sign that receives one of the three phantom bindus reads high, and any transit/strength logic that keys off SAV thresholds (the classic 25/28/30-bindu cutoffs) will be subtly miscalibrated. Fix is to correct the two array literals.

### Julian Day and UT conversion

`birthInputToJulianDay` subtracts the timezone from decimal local hours to get UT, then adjusts the calendar date when UT crosses midnight in either direction. The rollover math is correct: `new Date(y, oneIndexedMonth, 0).getDate()` returns the last day of that one-indexed month (JS day-0 = last day of the prior 0-indexed month), and the validator's timezone range (-12..+14) keeps UT within a single ±24h correction, so the single-step adjustment is sufficient. No day-rollover bug here.

### Dasha birth instant is rebuilt in server-local time

The chart's Julian Day is computed correctly in UT, but the API route independently reconstructs the birth moment for the dasha:

```ts
const birthDate = new Date(year, month - 1, day, hours, minutes, seconds || 0)
const dashaTree = computeVimshottari(moonPlanet.longitude, birthDate)
```

`new Date(y, m, d, h, ...)` interprets the components in the *server's* local timezone, not the birth timezone. `computeVimshottari` anchors the entire mahadasha/antardasha/pratyantardasha layout to this instant and the route serializes every boundary with `toISOString()` (UTC). So the same birth input produces dasha dates that shift by the server's UTC offset — a machine in IST and a machine in UTC return different timelines for identical input. That contradicts the deterministic premise of the feature. Build the instant in UT to match `birthInputToJulianDay` (e.g. `Date.UTC(...)` with the timezone subtracted), so the dasha anchor equals the same physical moment used for the planetary positions.

### Ephemeris source: silent Moshier fallback

`computePlanetPositions` requests `SEFLG_SWIEPH`, but nothing calls `swe_set_ephe_path` and no `.se1` files ship with the repo or Docker image. Running `swe_calc_ut` in this state returns valid data with the `SEFLG_MOSEPH` bit set in `rflag` — the library silently falls back to its built-in Moshier model. Two consequences: the "Swiss Ephemeris" precision claim in the file headers is inaccurate (Moshier is ~arcsecond-accurate for modern dates, fine for jyotish but not the Swiss files), and the `if ('error' in result) throw` guard never fires on fallback because `swisseph-v2` doesn't attach an `error` key when it degrades gracefully. Decide intent: bundle ephemeris files and set the path for true Swiss precision, or switch to `SEFLG_MOSEPH` explicitly and adjust the docs.

### Not reviewed in depth

The UI components under `app/compute/` and the tracked one-line edits to `app/api/charts/route.ts`, `app/api/runs/*`, and `engine/orchestrator.ts` were not scrutinized for math correctness; they don't carry astrological computation. No automated tests accompany the engine — given the density of classical rules and the bugs found, a fixture-based test suite comparing D1/D9/D30 and SAV against a known reference chart would have caught all five confirmed math errors.
