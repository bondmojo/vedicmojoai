# Duration Analysis — 3-agent sequential pipeline

A new sibling feature to the 18-agent wave pipeline: a practitioner picks a chart, date range,
life domain, optional symptoms, and a question, and the system deterministically slices the
stored Vimshottari dasha tree, builds a transit overlay, then runs up to three sequential LLM
agents (DA-1 domain analyser → DA-2 symptom validator → DA-3 future analyser) with SSE progress
and a follow-up chat. The engine (`slicer`/`transitOverlay`/`extractor`/`index`), five API routes,
two UI pages, three prompt files, the Prisma models, the migration, and the seed rows are all in
place, and the deterministic pieces (overlap slicing, sort, category isolation, yoga substrate
detection, BAV lookup) are largely faithful to the design.

Watch for: the DA-1 output contract is inconsistent with what the UI reads — `PeriodAnalysis`
requires `transitContext` and `lordAnnotations` on every period, but the DA-1 prompt never asks
the model to emit them and the pipeline never merges them in, so the period table's Transit column
is permanently dead (confirmed). Malformed LLM JSON is stored as `{ raw_content }` and the pipeline
*continues* rather than failing, which both diverges from the design's error table and crashes the
results page on `da1.period_analysis.map` (confirmed). The SSE route reconstructs events from DB
polling and never emits `agent_start`, drops token/cost from `agent_complete`, and reports a generic
error string — three unmet Requirement-6 criteria (confirmed). The 200-period truncation happens but
the `truncated: true` awareness flag required by 2.13 is missing (confirmed).

## High-level view

The headline is a producer/consumer contract split around `PeriodAnalysis`. The type and the UI
treat each analysed period as self-contained — carrying its own `transitContext` (Saturn/Jupiter
house + BAV score) and `lordAnnotations`. But those two structures are only ever produced as
*separate* top-level JSON blocks fed *into* DA-1 (periodSlice carries lordAnnotations, transitOverlay
is its own array keyed by `adStart`). The DA-1 prompt's output schema omits both fields, so the LLM
neither copies them through nor is asked to, and nothing in `index.ts` stitches them back onto each
period after the fact. The result compiles (the fields are simply absent at runtime) but the Transit
column renders `—` for every row regardless of the overlay the pipeline correctly computed and stored.

Error handling is the second theme. The design's error table says invalid agent JSON should set
`status = failed` and emit `agent_error`; the implementation instead swallows the parse failure into
`{ raw_content }` and proceeds, so a bad DA-1 poisons DA-2/DA-3 and breaks the UI, and a bad DA-2
silently bypasses the symptom gate (fail-open).

SSE is functional but lossy. Because both the POST and override routes pass a no-op `emitEvent`, the
pipeline's rich events are dead code and the `/events` route is the sole emitter, deriving state from
polled DB columns. That derivation covers `connected`, `agent_complete`, `symptom_gate`,
`run_complete`, and a generic `agent_error`, but has no way to signal `agent_start` and no token/cost
or real error text to attach — so the running indicator never advances to DA-2/DA-3 and a failed run
leaves all dots pending.

The deterministic core is solid: the slicer's overlap test, ascending sort, and 200-cap match the
properties; the extractor's column isolation is clean; the transit overlay dedups AD boundaries,
reads Sade Sati from stored periods, and defaults BAV to -1; the override/resume path correctly adds
DA-3 tokens onto existing totals and flips `overrideApplied`. The migration carries both tables, all
three indexes, and the FKs, and the seed adds DA-1/2/3 rows. Smaller gaps: follow-up chat cost is
never rolled into analysis totals, Neechabhanga only implements the lagna-side half of the spec'd
cancellation rule, and requirements.md and design.md disagree on whether `ashtakavarga` belongs in
every category (the code follows design).

### The `transitContext` / `lordAnnotations` contract split (the core defect)

`lib/durationTypes.ts` declares `PeriodAnalysis` with `transitContext: TransitOverlay` and
`lordAnnotations: {...}` as **required** fields on every analysed period. The results page treats
them as authoritative:

```tsx
// app/duration-analysis/[id]/page.tsx — PeriodRow
const bavScore = period.transitContext?.saturnBavScore ?? -1
const saturnHouse = period.transitContext?.saturn?.houseFromLagna
```

But those fields are only ever produced as *inputs* to DA-1, as two independent top-level JSON blocks:

```
--- PERIOD TABLE ---     ← DashaSlice[]  (has lordAnnotations, NO transitContext)
--- TRANSIT OVERLAY ---  ← TransitOverlay[]  (separate array, keyed by adStart)
```

`DashaSlice` itself has no `transitContext` field, and the DA-1 prompt's `OUTPUT FORMAT` block lists
only `md/ad/pd/analysis/key_factors/transit_factors/activated_yogas/intensity/favorable/bahiranga/antaranga`
— it never asks the model to echo `transitContext` or `lordAnnotations`. `index.ts` then does a bare
`JSON.parse(da1Response.content)` and stores it unchanged. So at runtime every `period.transitContext`
is `undefined`, `bavScore` collapses to `-1`, and the Transit column renders `—` for every row even
though `buildTransitOverlay` computed the data correctly and it sits in `durationAnalysis.transitOverlay`.

The prompt actively reinforces the confusion. Its `INPUT FORMAT` claims "PERIOD TABLE — DashaSlice[]
with lordAnnotations **and transitContext** per entry" (there is no such per-entry field), and a RULE
tells the model that "`saturnBavScore` and `jupiterBavScore` in `transitContext`" indicate transit
quality — but BAV lives in the separate overlay array keyed by `adStart`, so the model would have to
join `period.ad.start` against `transitOverlay[].adStart` to find it, and it is never told to do that.

The clean fix is deterministic and belongs in the pipeline, not the model: after DA-1 returns, walk
`da1Output.period_analysis`, look up the matching `transitOverlay` entry by `ad.start === adStart`,
and attach `transitContext` (and the matching `lordAnnotations` from the slice) onto each period
before persisting. That makes the type honest, feeds the UI real data, and stops asking the LLM to
faithfully reproduce large nested objects. As written, `lordAnnotations` is likewise a required field
the model never emits — harmless only because the UI happens not to read it (it reads
`activated_yogas`, which the prompt *does* request).

### Invalid JSON is swallowed and the pipeline marches on

Every agent parse uses the same shape:

```ts
try { da1Output = JSON.parse(da1Response.content) as DA1Output }
catch { da1Output = { raw_content: da1Response.content } as unknown as DA1Output }
```

The design's error table is explicit: "LLM returns invalid JSON → Store `{ raw_content }` as agent
output, **set status=failed, emit agent_error**." The implementation stores `{ raw_content }` but then
*continues* — DA-1 garbage flows into DA-2 and DA-3, and the run ends `status='done'`. Two concrete
consequences: (1) the results page executes `da1.period_analysis.map(...)` on an object with no
`period_analysis`, throwing at render; (2) a malformed **DA-2** produces `symptom_diagnosis ===
undefined`, so the `if (symptomDiag && symptomDiag.found === false)` gate is skipped entirely and the
pipeline proceeds to DA-3 as though symptoms matched — a fail-open on the one gate the feature exists
to enforce. At minimum DA-1/DA-2 parse failures should set `status='failed'` and emit `agent_error`;
the UI should also defensively coerce `period_analysis ?? []`.

### SSE stream: three unmet Requirement-6 criteria

Both entry points pass `emitEvent: () => {}`, so the pipeline's own SSE emissions (which *do* carry
`agent_start` and per-agent tokens) are dead code. The `/events` route is the sole emitter and
reconstructs everything by polling DB columns every 2s:

```
connected                     → on open, from initial.status         ✓ (6.1)
agent_complete {agent_id}     → when da1/da2/da3 Output present       ✗ missing tokenIn/Out/costUsd (6.3)
symptom_gate {da2Output}      → when status=symptom_unmatched         ✓ (6.5), closes stream
run_complete {totals}         → when status=done                     ✓ (6.6)
agent_error {error:"...failed"} → when status=failed                 ✗ generic, no agent_id/message (6.4)
(agent_start)                 → never emitted                        ✗ (6.2)
```

There is no DB signal the route can turn into `agent_start`, so the running indicator never advances:
after DA-1 flips to done, DA-2/DA-3 sit at `pending` until they complete, and because the UI's
`agent_error` handler only flips agents whose status is `running` to `failed`, a run that dies before
any agent is marked running leaves every dot `pending`. `agent_complete` omitting the token/cost
payload means the live view can't show incremental spend even though the numbers are persisted. And
the error path can only ever say "Analysis pipeline failed" because the real exception message is
never written to the DB — worth adding a nullable error column and having the pipeline persist
`error.message` so the route can relay it with the offending `agent_id`.

### 200-period truncation drops the awareness flag

`sliceDashaTree` correctly caps at 200 by `pd.start` ascending (`results.slice(0, 200)`), satisfying
the truncation half of Req 2.13. The other half — "include a `truncated: true` indicator in the DA-1
context so the model is aware the analysis covers a partial window" — is nowhere: the slicer returns a
bare array, `buildDA1Prompt` injects it as-is, and no flag reaches the prompt. There is also no
user-facing signal that the window was clipped. The model will confidently analyse a partial range as
if it were the whole thing.

### Follow-up chat cost is not rolled up

`/chat` persists the assistant `DurationMessage` with `tokenIn`/`tokenOut`, but never updates
`totalTokenIn`/`totalTokenOut` on the analysis and never stores `response.costUsd` anywhere (the
message model has no cost column). Property 6 scopes the token identity to the pipeline run, so this
isn't a property violation, but analysis-level `totalCostUsd` will understate real spend once a
conversation gets going — a monitoring gap given Requirement 5 exists specifically for operators.

### Yoga activation and Neechabhanga

The substrate detection (parivartana via `mutualReception`, conjunction via `conjunctions`, Raja via
kendra+trikona `houseLords`, Dhana via 2/11 + 1/5/9) reads the deterministic relationship columns and
matches the design's rules. The single MD/AD-derived `activatedYogas` array is intentionally shared
across all three lord annotations (including `pdLord`, which is slightly misleading but documented).

Neechabhanga is partial. The code flags cancellation only when the debilitation-sign dispositor sits
in a kendra **from lagna**:

```ts
const cancellationLord = EXALTATION_SIGN_LORDS[lord]      // actually the debil-sign dispositor
if (KENDRA_HOUSES.has(cancellationPlanet.house)) { ...cancelled... }
```

Design 2.11 calls for "debilitation lord **or exaltation lord** ... in kendra from lagna **or Moon**";
the "or exaltation lord" and "or Moon" branches are absent, so genuine cancellations will be missed.
The `EXALTATION_SIGN_LORDS` map is misnamed — its values are the dispositors of each planet's
*debilitation* sign — but the values themselves are correct, so the check works as far as it goes.

### Deterministic pieces that hold up

The slicer's overlap predicate (`pdStart < dateTo && pdEnd > dateFrom`), empty-safe return, and
ascending sort satisfy Properties 1–2. `extractCategoryData` returns exactly base + per-category
extras with clean isolation and an exhaustiveness guard (Property 3), the only wrinkle being the
docs disagreement on `ashtakavarga`. `buildTransitOverlay` dedups AD boundaries into a `Map` so
`computeTransits` runs once per unique AD, reads Sade Sati phase from the stored `allPeriods`
(`"MMM YYYY"` parsed and extended to end-of-month) rather than re-scanning the ephemeris, pulls
`ashtamaShani`/`kantakaShani` straight from the transit result, and defaults BAV to `-1` on missing
data — matching Requirements 2.9/2.12 and the ephemeris-error error-table row. The
`computeTransits(moonSign, lagnaSign, birthYear, adDate)` call matches the real signature and field
names (`signNumber`, `houseFromLagna`, `houseFromMoon`, `retrograde`). The override/resume path
validates status both at the route and in `resumeDurationPipeline`, adds DA-3 tokens onto the stored
totals (`analysis.totalTokenIn + da3Response.tokenIn`), flips `overrideApplied`, and threads the DA-2
mismatch into a prompt preamble — upholding the Property 5 override exception. Chat correctly rejects
non-`done` status before creating any message (Property 8) and appends user-then-assistant in order
(Property 7). The migration carries both tables, all three indexes, and the FKs (Req 10), and the
seed upserts DA-1/2/3 at the specified models/temperatures (Req 10.4).
