# Time-based special lagnas, Rahu co-lord, and ephemeris-driven transits

This change replaces three approximate computation shortcuts with correct classical formulas: Bhava/Hora/Ghati Lagna now advance from Sun's sidereal longitude at sunrise (BPHS Ch.5), not from the lagna; Varnada Lagna uses Hora Lagna (not D9) as its second input; and Sade Sati / Moon / Ascendant transits use real ephemeris sign-ingress moments found by bisection rather than fixed durations. A `sunriseMode` switch allows toggling between real astronomical sunrise (default) and JHora's fixed 6 AM convention. Rahu is added as the Aquarius co-lord for arudha computation, aligning with Jagannatha Hora.

**Watch for:** confirmed: `computeSingleArudha` docstring describes "prefer co-lord that does NOT trigger an exception" but the code unconditionally uses the co-lord — these are contradictory and the docstring will cause misimplementation; confirmed: `prevSignChange` epsilon reads (`entryJd + 0.001`, `entryJd + COARSE/10`) are unsafe for fast-rising ascendant signs where the coarse step is comparable to the sign duration; confirmed: silent sunrise fallback means a failed `swe_rise_trans` call returns `sunriseMode: 'precise'` in the output while having used the 6 AM approximation; confirmed: per-varga arudha cast to `PlanetPosition[]` is type-unsound and hides future breakage.

---

## High-level view

The time-based lagna engine now anchors to `sunLongitudeAtSunrise` and `elapsedHoursSinceSunrise`, matching the BPHS derivation. The two inputs travel from `computeSunrise` through `index.ts` into `computeSpecialLagnas`, replacing the old `birthTimeSeconds` parameter. The JHora-mode fallback in `computeSunrise` silently swallows `swe_rise_trans` failures and emits 6 AM without any warning in the returned data — the output `sunriseMode` field reflects what was _requested_, not what was _used_.

The `arudhaFromLord` extraction makes the count-and-reflect arithmetic auditable. The co-lord selection in `computeSingleArudha` is now simpler ("always use co-lord when present") than the docstring describes, and those two descriptions are now contradictory.

The transit bisection finds real ephemeris sign-ingress moments. Saturn retrograde re-entries are correctly merged when the fragment gap is under 240 days. The Moon and ascendant listings use `prevSignChange` to back-locate the start of the current sign, but the callers then read the sign at `entryJd + epsilon` rather than at the returned JD directly — for the ascendant, where sign durations can be under an hour, the coarse step size makes this unsafe.

Projecting special lagnas and upagrahas into divisional charts via `vargaSignForLongitude` is geometrically correct for points with real ecliptic longitudes. Karakamsa (`KS`) is stored as `(d9AKSignNumber - 1) × 30` — the start of a D9 sign expressed as a D1 longitude. Projecting this into D4, D7, D10, D30 produces results with no classical basis.

1. **`prevSignChange` epsilon read** — After bisection converges to sub-microsecond precision, the callers read `signAt(entryJd + 0.001)` (Moon) and `signAt(entryJd + COARSE/10)` (ascendant, = 1 minute). For ascendant signs that last under an hour at high latitudes, a 1-minute offset can land in the next sign. Read `signAt(entryJd)` directly; the bisection is precise enough.

2. **`arudhaFromLord` zero-lordCount guard needs a BPHS comment** — `lordCount` is forced to 12 when it would be 0 (lord in same sign as house). This is correct — BPHS treats "0 signs away" as "12 signs away" — but the code arrives at the right answer via an implicit chain that looks like a guard against modular zero, not a deliberate classical rule. Future editors will question it. Add the BPHS reference explaining why `lordCount = 0` must become 12.

3. **`computeSingleArudha` docstring vs. implementation** — The JSDoc says "prefer the co-lord that does NOT trigger an exception, matching JHora"; the implementation unconditionally returns `arudhaFromLord(houseSignNumber, coSign)` with no exception-check fallback. The docstring implies a primary-lord fallback that does not exist. Fix the docstring to match the simpler "always use co-lord" rule.

4. **Silent sunrise fallback** — When `swe_rise_trans` throws, `computeSunrise` falls back to 6 AM local with no indication. `index.ts` writes `sunriseMode: input.sunriseMode ?? 'precise'` to the output before calling `computeSunrise`, so a failed precise request silently claims to be precise. Add a `sunriseFallback: boolean` flag to the return value, or surface the fallback in the output object.

5. **Karakamsa projected into non-D9 vargas** — `KS` longitude is `(d9AKSignNumber - 1) × 30`, a D9-derived value stored as a pseudo-D1 longitude. For D9 the projection is coincidentally correct; for D4, D7, D10, D30 it is arbitrary. Either omit KS from per-varga projection, or add a comment flagging the non-classical semantics.

6. **Indu Lagna Rahu/Ketu edge case undocumented** — `totalIndu % 12 || 12` maps a sum of 0 (only when both 9th lords are Rahu or Ketu, whose INDU_VALUE is 0) to 12, placing IL in Moon's own sign. This is a defensible fallback but has no classical citation. Add a comment or verify against a source.

7. **Per-varga arudha type cast** — `dc.planets.map(...) as Parameters<typeof computeArudhaPadas>[1]` casts objects missing `longitude`, `latitude`, `speed`, `retrograde`, `sign`, `degreeInSign`, `house` to `PlanetPosition[]`. It works today because `computeArudhaPadas` only reads `planet` and `signNumber`, but the cast masks the mismatch. Narrow the `computeArudhaPadas` signature to accept `{ planet: string; signNumber: number }[]`.

### `arudhaFromLord` arithmetic and the zero-lordCount case

The reflect-and-count formula is `arudha = ((lordSignNumber - 1 + lordCount) % 12) + 1`. When the lord is in the same sign as the house, `lordCount` is forced to 12 rather than 0. This yields `arudha = lordSignNumber = houseSignNumber`, so exception 1 fires and the 10th from the house is used — the classical BPHS rule. BPHS treats "0 signs away" as equivalent to "12 signs away" (a sign is not its own arudha, so the 10th substitute applies). The code is correct but the comment only notes _what_ is done, not _why_ zero must become 12. A reader who knows modular arithmetic will read the guard as a defensive zero-check rather than a deliberate classical convention.

Exception 2 checks `arudha === seventhFromHouse` after exception 1 has potentially already modified `arudha`. This is the correct ordering per classical sources: apply the "same sign" exception first, then check whether the result lands on the 7th.

### Co-lord selection: docstring vs. implementation

`computeSingleArudha` has two competing descriptions. The JSDoc block (spanning ~8 lines) describes a preference algorithm that picks whichever co-lord avoids an exception; the inline comment in the body says "always uses the co-lord". The code does the latter: `coSign !== null` → unconditionally return `arudhaFromLord(houseSignNumber, coSign)`. The JHora test results confirm this for Aquarius houses. The docstring is stale from an earlier iteration and implies a primary-lord fallback that does not exist in the code.

### Transit bisection: epsilon reads and ascendant sign durations

`prevSignChange` runs 42 bisection iterations, reaching 2^−42 day ≈ sub-microsecond precision. It returns `hi` — the first JD confirmed inside the current sign. The Moon caller reads `moonSign(entryJd + 0.001)` (= ~86 seconds ahead) and the ascendant caller reads `ascSign(entryJd + COARSE/10)` (= 1 minute ahead). For the Moon these offsets are irrelevant — the Moon won't change sign in 86 seconds. For the ascendant at latitudes above ~50° in fast-rising signs (Sagittarius–Capricorn near the northern horizon), a sign can transit in 45–55 minutes. A 1-minute offset on a `prevSignChange` result that itself used a 10-minute coarse step could land in the adjacent sign. The safer pattern is `signAt(hi)` directly, with the bisection's precision as the guarantee.

In `nextSignChange`, `startJd + coarseStepDays` is passed as the initial `hi`. For the ascendant with COARSE = 10 minutes, this step is smaller than the fastest-rising sign, so the while loop will terminate in a finite number of iterations — but the loop is bounded only by `guard < 5000`, which at 10-minute steps covers ~35 days. That's intentional for the Sade Sati use case but is also applied unchanged to the ascendant. A step that's appropriate for Saturn (~10 days) is 1440× larger than needed for the ascendant; the resulting ephemeris call count for a full 12-sign ascendant listing (~12 bisections × 42 iterations) is still manageable, but the asymmetry is worth documenting.

### Varnada Lagna arithmetic trace

The Nehru example trace (Cancer=4 lagna, Pisces=12 HL): `lagnaOdd=false`, `horaOdd=false`, `A = 13-4 = 9`, `B = 13-12 = 1`, same parity → `C = 10`, `Cn = 10`, lagna is even → `Varnada = 13-10 = 3 = Gemini ✅`. The `varnadaSignNumber < 1` guard can fire when `Cn = 12` for an even lagna: `13 - 12 = 1`, which is already valid — the guard fires only for `Cn > 12`, which is unreachable since `Cn = ((C-1) % 12) + 1` is bounded to 1–12. The guards are harmless but unnecessary.

### Varga projection of special lagnas

BL, HL, GL, SL, VL, IL, BBL, PL all have genuine ecliptic longitudes and project correctly through `vargaSignForLongitude`. KL (aliased to GL) shares GL's longitude and is fine. KS is stored as `(d9AKSignNumber - 1) × 30`, the longitude of the _start_ of the D9 Atmakaraka sign expressed in D1 terms. For D9 this projects back to approximately the right sign (the D9 computation will land in the D9 sign that starts at that longitude), but only because the stored value is constructed from a D9 sign number. For D4, D7, D10, D30 the result is determined by where that pseudo-longitude falls in those divisional schemes — classically meaningless and potentially misleading in a displayed chart.

### Silent sunrise fallback and output integrity

`computeSunrise` has three code paths: `jhora` (explicit 6 AM), `precise` (swe_rise_trans succeeds), and the silent fallback inside the `catch` block (swe_rise_trans fails → 6 AM). The `try` block sets `sunriseJD = julianDay` as the initial fallback before the `swe_rise_trans` call, meaning a partial failure (call returns without throwing, but `transitTime` is not a number) results in `sunriseJD = julianDay` — the birth moment itself — which is a third distinct behavior not documented anywhere. If `transitTime` is absent and no exception is thrown, `elapsedHoursSinceSunrise` in `index.ts` becomes `(julianDay - julianDay) × 24 = 0`, placing all time-based lagnas at the Sun's position at birth with zero elapsed time. This is wrong in a different way from either the precise or JHora result.
